# QEMU 源码解析：简单修改与实验

理论学习之后，最好的巩固方式，就是动手实践。通过对 QEMU 源码，进行一些简单的、无伤大雅的修改和实验，可以极大地加深我们对其内部工作机制的理解。这是一个将抽象概念，与具体代码行为，联系起来的过程。

**在开始之前，请确保你已经成功地编译了 QEMU 的源码。**

## 实验一：在指令翻译器中添加日志

**目标**: 亲眼观察 QEMU 的 TCG 前端，是如何将目标架构的指令，翻译成 TCG 微操作的。

**步骤**: 
1.  **定位翻译文件**: 找到你所关心的目标架构的指令翻译文件。例如，对于 ARM64，这个文件是 `target/arm/translate.c`。

2.  **选择一条指令**: 选择一条简单的、你想要观察的指令。例如，`ADD` 指令。在文件中，搜索处理 `ADD` 指令的翻译函数（函数名通常会包含 `trans_ADD` 这样的关键字）。

3.  **添加日志代码**: 在这个翻译函数的开头，添加一条 `printf` 或 `qemu_log` 语句，来打印一些信息。例如：

    ```c
    // 在 target/arm/translate.c 的某个 ADD 指令翻译函数中
    static void trans_ADD_some_variant(DisasContext *s, arg_ADD_some_variant *a) {
        // 添加我们的日志
        printf("--- Translating an ADD instruction at PC=0x%llx ---\n", (unsigned long long)s->pc);

        // ... 原有的 TCG 微操作生成代码 ...
    }
    ```

4.  **重新编译 QEMU**: 在 QEMU 的构建目录中，运行 `make` 来重新编译你的修改。

5.  **运行测试程序**: 运行一个会执行到 `ADD` 指令的、简单的裸机程序。

**观察结果**: 
当你运行 QEMU 时，你应该能在控制台上，看到你添加的 `printf` 日志被打印出来。这直观地证明了：
*   QEMU 的 CPU 执行循环，在遇到一个未被翻译的代码块时，确实调用了 `translate.c` 中的相应函数。
*   这个翻译过程，是在**运行时**动态发生的。

## 实验二：修改 MMIO 设备的行为

**目标**: 理解 QEMU 是如何通过 `MemoryRegion` 和回调函数，来模拟设备 I/O 的。

**步骤**: 
1.  **定位设备源码**: 找到一个简单的、QEMU 内置的设备模型的源码。一个很好的例子，是 `pl011` 串口设备，其源码位于 `hw/char/pl011.c`。

2.  **找到 I/O 回调函数**: 在该文件中，找到用于处理 MMIO 读写的 `read` 和 `write` 函数。对于 `pl011`，它们可能是 `pl011_read` 和 `pl011_write`。

3.  **修改回调逻辑**: 在 `pl011_write` 函数中，添加一些自定义的逻辑。例如，当写入到数据寄存器 (`UARTDR`) 的字符，是字母 `'a'` 时，我们将其替换为 `'z'`。

    ```c
    // 在 hw/char/pl011.c 的 pl011_write 函数中
    static void pl011_write(void *opaque, hwaddr offset, uint64_t value, unsigned size) {
        PL011State *s = opaque;
        
        if (offset == 0x00) { // UARTDR, a.k.a. the data register
            // 添加我们的修改逻辑
            if (value == 'a') {
                value = 'z';
            }
            // ... 原有的将 value 发送到后端字符设备的代码 ...
        }
        // ... 其他寄存器的处理 ...
    }
    ```

4.  **重新编译并运行**: 重新编译 QEMU，并运行我们之前那个打印 “Hello, World!” 的裸机程序。

**观察结果**: 
这一次，你应该会在控制台上，看到输出的 “Hello, World!” 变成了 “Hello, World!”（假设原始字符串中不包含 'a'）。如果你修改裸机程序，使其打印 “banana”，那么输出，应该会变成 “bznznz”。

这个实验，清晰地展示了：
*   客户机操作系统（或裸机程序）对特定物理地址的“写”操作，是如何被 QEMU 拦截，并分派到对应的设备模型的 `write` 回调函数中的。
*   设备模型，拥有对 I/O 操作的完全控制权，它可以检查、修改、记录或丢弃这些操作。

## 实验三：使用 GDB Stub 进行调试

**目标**: 学习如何使用 QEMU 内置的 GDB Stub，来对在虚拟机中运行的代码，进行源码级的调试。

**步骤**: 
1.  **编译带调试信息的客户机程序**: 在使用交叉编译器，编译你的裸机程序 `hello.c` 时，务必加上 `-g` 标志，以包含调试符号。
    `arm-none-eabi-gcc -g -o hello.elf hello.c ...`

2.  **以调试模式启动 QEMU**: 
    *   `-s`: 这是 `-gdb tcp::1234` 的简写。它会启动 QEMU，并使其 GDB 服务器，在本地的 1234 端口上，进行监听。
    *   `-S`: 这个选项，会使 QEMU 在启动后，**立即暂停** CPU 的执行，等待 GDB 客户端的连接。

    ```bash
    ./my-qemu-system-aarch64 -M my-simple-arm-machine -kernel hello.elf -nographic -s -S
    ```

3.  **启动 GDB 客户端**: 在另一个终端窗口中，启动一个针对 ARM 架构的 GDB 客户端，并加载带有调试符号的 `.elf` 文件。

    ```bash
    gdb-multiarch hello.elf
    ```

4.  **连接到 QEMU**: 在 GDB 的提示符下，输入以下命令，来连接到正在等待的 QEMU 实例。

    ```gdb
    (gdb) target remote :1234
    ```

5.  **开始调试**: 连接成功后，你就可以使用所有标准的 GDB 命令，来对你的**裸机程序**，进行调试了！
    *   `(gdb) b _start`: 在 `_start` 函数处，设置一个断点。
    *   `(gdb) c`: 继续执行，程序应该会停在你设置的断点处。
    *   `(gdb) layout src`: 显示源代码窗口。
    *   `(gdb) stepi` 或 `si`: 单步执行一条汇编指令。
    *   `(gdb) info registers`: 显示所有寄存器的值。

**观察结果**: 
你可以在一个终端中，看到 GDB 的源码级调试界面；在另一个终端中，看到 QEMU 的输出。你能够精确地，控制客户机程序的每一步执行，并观察其对模拟硬件（如串口）所产生的影响。

## 总结

通过动手修改 QEMU 的源码，并进行实验，是戳破虚拟机“黑盒子”的最好方法。

*   **添加日志**，是最简单、最有效的，观察代码执行路径的方式。
*   **修改设备模型**，可以让你直观地，理解 MMIO 的工作原理。
*   **使用 GDB Stub**，则为你提供了一个极其强大的、能够深入到客户机代码内部的“显微镜”。

这些简单的实验，仅仅是探索 QEMU 这个巨大宝库的开始。它们为你提供了一个入口，让你能够开始阅读、理解、并最终有能力去修改和扩展这个强大的开源项目，从而构建出你自己定制的、独特的虚拟化和系统模拟工具。
