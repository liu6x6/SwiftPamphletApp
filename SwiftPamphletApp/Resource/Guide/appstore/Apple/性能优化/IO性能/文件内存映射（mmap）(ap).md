# mmap：文件读取的终极魔法 (内存映射)

在前面的章节中，我们提到用 `Data(contentsOf:)` 一次性读取 2GB 的视频文件会立刻导致 OOM（内存耗尽崩溃）。

但在 iOS 系统框架极其底层的地方，当系统加载动辄几十 MB 的字体文件、极其庞大的核心动画框架二进制包时，它却一点也不卡，内存也没见怎么涨。
这种底层黑魔法就是 **`mmap` (Memory-Mapped Files, 内存映射文件)**。

## 1. 为什么传统的读取那么笨拙？

传统的读文件（如 `FileHandle` 或 C 语言的 `fread`），数据流动是极其繁琐的：
1. 发起系统调用（上下文切换到极慢的内核态）。
2. 硬盘控制器开始寻道读数据。
3. 把硬盘数据先读到操作系统内核的极小缓冲区里（Page Cache）。
4. 再从内核缓冲区，老老实实地**拷贝**到你的 App（用户态）申请的内存变量（Data）中。

如果文件极大，你的 App 内存必然爆炸。

## 2. mmap 到底施了什么魔法？

`mmap` 是一条极其特殊的 Unix 级别系统指令。
它的作用是：**它不是去“读”文件，而是直接把硬盘上那个文件的物理存储区域，在虚拟内存（Virtual Memory）上“画了一个虚假的框（映射）”。**

当你在 Swift 中通过 `mmap` 的特性拿到了一个看似巨大的 2GB `Data` 变量时：
*   **实际占用的物理内存几乎为 0**！系统只是给了你一个 2GB 的虚拟地址区间。
*   当你使用数组下标 `data[5000]` 试图读取第 5000 个字节时，这块虚拟内存会发生一次轻微的“缺页中断 (Page Fault)”。
*   操作系统的极其底层的内存管理器会介入，瞬间直接从硬盘上的对应扇区里，极其精准地把包含那个字节的一小块数据页面（通常是 4KB 或 16KB）搬到物理内存里。
*   一旦内存吃紧，系统又会极其智能地把那些不再访问的内存页面从物理内存中释放掉。

整个过程**没有任何用户态到内核态的冗余数据拷贝**，并且利用了操作系统最顶级的内存调度智能！

## 3. 在 Swift 中优雅地使用 mmap

万幸的是，Apple 在高层的 Foundation 框架中极其优雅地封装了这个 C 语言的底层怪物。

只需在 `Data` 的初始化方法中加一个参数：**`.mappedIfSafe`** 或 **`.alwaysMapped`**。

```swift
import Foundation

let hugeFileURL = URL(fileURLWithPath: "/path/to/very/large/file.db")

do {
    // 关键魔法就在这个参数：.alwaysMapped
    // 这行代码执行速度是纳秒级的！不管文件有 1G 还是 10G，瞬间返回！
    let memoryMappedData = try Data(contentsOf: hugeFileURL, options: .alwaysMapped)
    
    // 打印大小，依然显示是 2GB
    print("映射的文件大小: \(memoryMappedData.count) 字节")
    
    // 你可以像操作普通数组一样，瞬间跳转到极远的地方读取一个字节
    // 此时硬盘才真正发生转动和读取 (Page Fault)
    let byteInTheMiddle: UInt8 = memoryMappedData[1_000_000]
    
} catch {
    print("内存映射失败")
}
```

## 4. 适用与不适用场景

**极其适用（杀手级应用）：**
*   **巨型只读数据库引擎**：如 SQLite 的底层、庞大的词典检索库。
*   **音视频处理框架**：在极大的视频流中随机跳转 (Seek) 并读取片段帧，而不把整个视频读进内存。
*   **进程间通信 (IPC)**：两个不同的 App 映射了同一个底层文件，A 改了数据，B 的内存里不用刷新就能瞬间看到改动。

**极其不适用（性能灾难）：**
*   **读取极其微小的碎片文件**（小于一页，如几个字节的 txt）。建立映射的系统调度开销反而大于直接老老实实读进来。
*   **顺序流式读取并整体解析**：如果你打算把这 2GB 的数据从头到尾按顺序全遍历一遍，并且扔进一个 JSON 解析器全部转化成对象，那 mmap 也没用，你的内存最终还是会因为那些被解析出来的对象而爆炸。流式读取请老老实实用 `FileHandle` 流。
