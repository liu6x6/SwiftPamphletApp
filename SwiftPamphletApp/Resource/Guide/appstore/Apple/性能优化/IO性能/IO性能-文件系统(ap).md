# iOS / macOS 底层文件系统 (APFS) 及其对性能的影响

在谈论“文件读写慢”之前，高级开发者必须深刻理解他们的代码是运行在什么样的一层“土壤”上的。
自 2017 年 (iOS 10.3 / macOS High Sierra) 起，Apple 平台全线从古老的 HFS+ 切换到了现代的、专为闪存 (SSD) 优化的 **APFS (Apple File System)**。

了解 APFS 的特性，可以让你白嫖许多极其巨大的 IO 性能红利。

## 1. 克隆与写时复制 (Copy-on-Write)

这是 APFS 最为人称道的“黑科技”。

在旧的文件系统中，如果你把一个 1GB 的视频文件 `copy` 到同一个硬盘的另一个文件夹，系统必须老老实实地从硬盘读出 1GB 的电信号，再写回 1GB 的电信号。这极其耗时且磨损闪存寿命。

**在 APFS 中，同卷内的复制是瞬间完成的 (Zero-time copy)！**

*   **克隆 (Clones)**：当你使用 `FileManager.default.copyItem(at:to:)` 时，底层并不会真的去复制那 1GB 的数据。APFS 只是在文件分配表里新建了一个极小的指针节点，指向了硬盘上同一块物理数据块。
*   **写时复制 (COW)**：只有当你想“修改”其中一个副本（比如截取了视频的前半段并保存）时，系统才会在那一瞬间，把发生改变的数据块真正分配新的物理空间写进去。

**性能优化启示**：
在开发 App 时，如果你需要对大量原始素材（如图片滤镜编辑应用中的原图）建立多个版本的工作副本，直接放心大胆地用 `FileManager.default.copyItem` 复制文件即可，不要自己去写极其复杂的内存复用逻辑。底层的文件系统已经帮你把这件事的性能做到了极致。

## 2. 极其安全的原子级保存 (Atomic Save)

在早期的 App 开发中，如果你正在往磁盘写入一个很重要的用户存档文件（写入过程耗时 2 秒），如果在第 1 秒的时候手机没电关机了，这个文件就会“写一半”，从而损坏变成乱码。

APFS 支持极其安全的“写入与重命名”事务机制。
这在 Swift 的高层 API 中被封装为了 `Data.write(to:options: [.atomic])`。

*   **底层原理**：当你开启 `atomic` 时，系统其实是先在一个不可见的临时路径（如 `/.tmp_xxxx`）新建一个文件并慢慢写入。
*   只有当数据**完全落盘**且校验无误的那一个原子纳秒，系统才会利用 APFS 的快速元数据交换能力，瞬间把原来的旧文件删掉，把这个临时文件重命名为正式的文件名。
*   即使中间断电，原来的旧文件依然完好无损。

**性能代价与抉择**：
虽然原子写入极其安全，但它涉及两次完整的文件系统操作（写一个新文件 + 删一个老文件）。如果你的 App 需要每秒钟向磁盘高频地写入微小的日志流数据（如 10 毫秒记录一次），使用原子写入将导致极其严重的 IO 性能灾难，此时应该使用 `FileHandle` 追加模式 (Append) 而非全量复写。

## 3. 稀疏文件 (Sparse Files) 支持

如果你的 App 是一个下载器，你需要预先在硬盘上占据一个 10GB 的“空坑”，然后用多线程去填满里面不同的碎块。
如果你去手写 10GB 的 `0x00` 来占位，不仅慢，而且毫无意义。

APFS 支持稀疏文件。你可以向系统声明一个 10GB 的文件节点，但如果你没有往里面写真实数据，这个文件在物理硬盘上占用的空间其实是 0 字节。
使用 C 底层的 `ftruncate` 或者是 `FileManager.default.createFile(atPath:contents:nil)`，你可以极其快速地建立大文件的占位符。

## 4. 文件级别的加密 (File-Level Encryption)

在 APFS 中，加密是在极低的文件系统驱动层完成的。
你在给 iOS 的沙盒文件设置 `FileProtectionType`（例如 `.completeFileProtection` 锁屏后极其严格的安全保护）时，不需要自己在应用层写 AES 加密算法。当你把 `Data` 交给系统时，系统会利用设备自带的 Secure Enclave 和加密硬件引擎，在写入闪存的那一瞬间极速加密，几乎不消耗主 CPU 资源。
