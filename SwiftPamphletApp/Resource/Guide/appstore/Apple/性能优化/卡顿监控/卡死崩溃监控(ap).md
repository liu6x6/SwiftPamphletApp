# 卡死崩溃监控

除了常规的、可以被 Exception Handler 捕获的“崩溃”（Crash），在 App 的实际运行中，还存在一种更为棘手的问题——“卡死”（ANR - Application Not Responding）。卡死是指 App 的主线程被长时间阻塞，导致界面完全无法响应用户操作，最终被系统或用户强行终止。

对于用户来说，卡死和崩溃的体验同样糟糕。因此，建立一套有效的卡死监控和诊断机制，对于提升 App 的稳定性至关重要。

## 卡死与崩溃的区别

| 特性 | 常规崩溃 (Crash) | 卡死 (ANR) |
| :--- | :--- | :--- |
| **原因** | 非法内存访问、未捕获的异常、强制解包nil等 | 主线程执行了耗时操作（如同步的网络请求、大量I/O、复杂计算）或陷入死锁 |
| **表现** | 应用瞬间闪退 | 界面冻结，无法响应任何触摸事件，最终被系统或用户杀死 |
| **捕获方式** | 可以通过 `NSSetUncaughtExceptionHandler` 或 Signal Handler 来捕获 | 无法通过常规的崩溃处理机制捕获，需要专门的监控方案 |

## 卡死监控的核心原理

卡死监控的核心，在于**判断主线程是否在预期的时间内，完成了其任务循环**。这通常是通过**子线程**来“反向”监控**主线程**的状态来实现的。

目前主流的卡死监控方案，大多基于对 **RunLoop** 状态的监控。

### 基于 RunLoop 的监控方案

1.  **开启一个子线程**: 创建一个专门用于监控的、独立的子线程。

2.  **注册 RunLoop Observer**: 在这个子线程中，向**主线程**的 RunLoop，注册一个 `CFRunLoopObserver`。

3.  **监控 RunLoop 状态**: 这个 Observer 会被设置为，在主线程 RunLoop 的几个关键状态切换时，得到通知。我们主要关心两个状态：
    *   `kCFRunLoopBeforeSources`: 即将处理输入源事件（如触摸事件）。
    *   `kCFRunLoopAfterWaiting`: 刚刚从休眠状态中被唤醒。

4.  **设置“哨兵”**: 
    *   在子线程的循环中，不断地检查主线程 RunLoop 的状态。
    *   当检测到主线程的 RunLoop 状态，从 `kCFRunLoopAfterWaiting` 切换到 `kCFRunLoopBeforeSources` 时，我们认为主线程即将开始处理一个事件。此时，我们在子线程中，设置一个“哨兵”状态（例如，一个布尔值标志位），并记录下当前的时间戳。
    *   我们期望主线程在处理完这个事件后，会再次进入休眠（`kCFRunLoopAfterWaiting`）或处理下一个事件。如果在我们设定的一个**超时阈值**（例如，3秒）之后，这个“哨兵”状态仍然没有被改变，我们就认为主线程已经被“卡死”了。

5.  **捕获堆栈并上报**: 一旦判定为卡死，子线程就会立即获取当前**主线程**的函数调用堆栈，并连同其他上下文信息（如设备信息、App 版本、前台/后台状态等），一起保存到本地或上报到服务器。

        A[循环开始] --> B{主线程RunLoop状态?}

## 崩溃监控

对于常规的崩溃，我们可以通过注册相应的处理函数，来在 App 崩溃前，捕获到尽可能多的信息。

### 1. `NSSetUncaughtExceptionHandler`

*   **作用**: 用于捕获未被 `try-catch` 捕获的 Objective-C 和 Swift 异常（`NSException`）。
*   **实现**: 在 `application(_:didFinishLaunchingWithOptions:)` 中，设置一个全局的异常处理函数。在这个函数中，我们可以获取到异常的名称、原因和调用堆栈。

### 2. Signal Handler

*   **作用**: 用于捕获由操作系统内核发出的、更为底层的“信号”（Signal）。这些信号，通常是由非法的内存访问（如 `SIGSEGV` - 段错误）、非法指令（如 `SIGILL`）等硬件级错误所触发的。
*   **实现**: 使用 `signal()` 或 `sigaction()` 函数，为 `SIGABRT`, `SIGBUS`, `SIGFPE`, `SIGILL`, `SIGSEGV`, `SIGTRAP` 等多种信号，注册我们的处理函数。在处理函数中，我们可以捕获到导致崩溃的线程的完整调用堆栈。

### 崩溃日志的上报

在捕获到崩溃信息后，由于 App 即将终止，我们不能在处理函数中，进行复杂的、耗时的操作（如网络请求）。正确的做法是：

1.  将捕获到的所有信息（异常类型、堆栈、设备信息等），快速地、完整地**写入到本地的一个文件中**。
2.  在用户**下一次**启动 App 时，检查是否存在上次未上报的崩溃日志文件。
3.  如果存在，再将其通过网络，上报到我们的后台服务器。

## 总结

卡死和崩溃监控，是保障 App 线上稳定性的最后一道防线。

*   **卡死监控**: 核心是**在子线程中，通过监控主线程 RunLoop 的状态切换，来判断其是否发生了长时间的阻塞**。

*   **崩溃监控**: 通过注册 **`NSSetUncaughtExceptionHandler`** 和 **Signal Handler**，来分别捕获上层的 `NSException` 异常和底层的 Mach 异常信号。

*   **信息捕获**: 无论是卡死还是崩溃，最关键的信息，都是**发生问题时，所有线程（特别是主线程）的函数调用堆栈**。获取到完整的、符号化后的堆栈，是定位和解决问题的根本。

在实际项目中，我们通常会使用一些成熟的第三方 APM（Application Performance Monitoring）SDK，如 Firebase Crashlytics, Bugly, Sentry 等。这些 SDK 已经为我们封装好了上述复杂的监控和上报逻辑，并提供了强大的后台，来对收集到的问题，进行聚合、分类和分析。
