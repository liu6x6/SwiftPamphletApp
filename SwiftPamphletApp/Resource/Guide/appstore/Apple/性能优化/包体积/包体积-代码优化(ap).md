# 包体积优化：代码优化

除了资源和第三方库，我们自己编写的代码，也是构成 App 包体积的重要组成部分。通过一些编码和架构层面的优化，可以有效地减少最终可执行文件的大小。

## 1. 清理无用代码 (Dead Code)

这是最直接、最有效的代码优化手段。随着项目的迭代，必然会产生一些不再被任何地方调用的类、方法、属性或常量。这些“僵尸代码”不仅增加了包体积，也提高了项目的维护成本。

*   **静态分析工具**: 使用像 **Periphery** 这样的工具，可以自动化地扫描整个项目（包括跨模块），并找出那些编译器无法静态确定的无用代码。
*   **代码覆盖率**: 单元测试的覆盖率报告，可以帮助我们识别那些从未被执行到的代码路径。这些路径，是无用代码的“高嫌疑区”。
*   **人工审查**: 定期地进行代码审查，对于标记为 `@objc`、`dynamic` 或 `public` 的代码，要格外注意，确认它们是否真的需要如此高的动态性或可见性。

（更多详情请参阅 `Swift无用代码(ap).md`）

## 2. 利用 Swift 的语言特性

Swift 的一些语言特性，在设计上就考虑了性能和代码体积的优化。

*   **优先使用 `struct` 和 `enum`**: 值类型（`struct`, `enum`）相比于引用类型（`class`），通常具有更少的内存开销。更重要的是，它们的派发方式是**静态派发**。这意味着，编译器在编译时，就能确定具体调用的是哪个方法，从而可以进行更多的内联（inlining）和优化，链接器也能更彻底地进行“死代码剥离”。

*   **谨慎使用 `final` 和 `private`**:
    *   **`final`**: 当你确定一个类或方法，不会再被任何其他类继承或重写时，应该用 `final` 关键字来标记它。这会告诉编译器，可以将这个方法的调用，从动态派发，优化为更高效的静态派发。
    *   **`private` / `fileprivate`**: 尽可能地降低代码的访问级别。一个被标记为 `private` 的方法，其可见性被限制在当前文件或定义内，编译器可以更容易地判断其是否被使用，并进行优化。

## 3. 减少泛型的使用

泛型是 Swift 中一个极其强大的特性，但它也可能会带来包体积的膨胀。

*   **泛型特化 (Generic Specialization)**: 当你使用一个泛型函数或类型时（例如，`Array<Int>` 和 `Array<String>`），编译器会为每一个具体的类型（`Int`, `String`），生成一份独立的、特化版本的代码。如果你在代码中，使用了大量的、不同类型的泛型实例，就会导致最终的二进制文件中，包含许多份类似的、但又无法被合并的代码，从而增加包体积。

*   **优化建议**:
    *   **权衡利弊**: 在追求代码的抽象和复用性时，也要考虑到泛型可能带来的包体积成本。
    *   **类型擦除 (Type Erasure)**: 在某些场景下，可以使用“类型擦除”技术（如 `AnyPublisher`），来隐藏底层的具体泛型类型，从而减少需要特化的代码版本。

## 4. 优化代码结构

*   **代码复用**: 避免大段的、重复的代码块。将可复用的逻辑，抽象成独立的函数或方法。

*   **避免巨型函数**: 一个过于庞大和复杂的函数，不仅难以维护，也不利于编译器的优化。应该将其拆分成更小、更专注的函数。

## 5. 编译选项优化

在 Xcode 的 Build Settings 中，有一些与代码优化和包体积相关的编译选项。

*   **Optimization Level**: 在 Release 配置下，务必将优化级别设置为 `-Osize`（优化包体积）或 `-O`（优化性能）。这会开启一系列的编译器优化，包括死代码剥离、函数内联、循环展开等。

*   **Dead Code Stripping**: 确保在 Release 配置下，该选项（`DEAD_CODE_STRIPPING`）被设置为 `YES`。

*   **Generate Debug Symbols**: 在 Release 配置下，将该选项设置为 `NO`，可以移除最终二进制文件中的调试符号，从而减小体积。（注意：这会使得崩溃日志的符号化变得困难，通常需要配合 dSYM 文件来进行。）

## 总结

代码层面的包体积优化，是一个需要在**代码优雅性**、**性能**和**体积**之间，进行综合权衡的过程。

1.  **清理是基础**: 定期地、自动化地**清理无用代码**，是成本最低、收益最高的优化手段。

2.  **善用语言特性**: 充分利用 Swift 的**值类型**、**`final`** 和 **`private`** 等关键字，来帮助编译器进行更深度的优化。

3.  **警惕泛型膨胀**: 在享受泛型带来的便利时，也要意识到它可能带来的**代码体积膨胀**问题。

4.  **相信编译器**: 在 Release 模式下，充分信任并开启编译器的**优化选项**。

通过在日常开发中，养成良好的编码习惯，并结合静态分析工具进行定期的“体检”，我们可以有效地控制代码部分的体积增长，让我们的 App 保持“苗条”和健康。
