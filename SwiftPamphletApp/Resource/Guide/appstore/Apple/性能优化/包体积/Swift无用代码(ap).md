# Swift 无用代码检测与优化

随着项目迭代，代码库中不可避免地会积累一些不再被任何地方调用的“无用代码”（Dead Code）。这些代码不仅增加了项目的维护成本和编译时间，还会占用最终的包体积。因此，定期地检测和清理无用代码，是 App 包体积优化的重要一环。

对于 Swift 来说，由于其静态类型和编译期优化的特性，无用代码的检测相比 Objective-C 既有优势，也面临着新的挑战。

## 编译器优化：Dead Code Stripping

Swift 编译器（LLVM）自身就具备强大的无用代码剥离（Dead Code Stripping）能力。在编译的链接阶段，链接器会进行“死代码剥离”，自动地移除那些在编译单元内从未被访问过的函数和数据。

*   **工作原理**: 链接器会构建一个符号依赖图。从程序的入口点（如 `main` 函数）开始，遍历所有可达的（reachable）函数和全局变量。所有不可达的符号，最终都会被认为是无用代码，并从最终的可执行文件中移除。
*   **优化级别**: 在 Release 配置下（Optimization Level 设置为 `-O` 或 `-Osize`），这个功能是默认开启的。

## Swift 无用代码检测的难点

尽管编译器能做很多工作，但仍然有许多类型的无用代码，是编译器无法静态地、安全地判断和移除的。这主要是由于 Swift 的动态特性和与 Objective-C 的互操作性。

1.  **动态派发 (Dynamic Dispatch)**: 
    *   对于 `class` 中未使用 `final` 或 `private` 标记的方法，编译器默认会使用动态派发（通过 v-table）。这意味着，一个方法的调用，是在运行时才确定具体实现的。因此，即使一个 `public` 或 `internal` 的方法在当前模块中从未被直接调用，编译器也无法确定它是否会在运行时被其他模块、或通过 Objective-C 运行时被间接调用。

2.  **Objective-C 运行时**: 
    *   通过 `@objc` 关键字暴露给 Objective-C 的 Swift 代码，或者继承自 `NSObject` 的类，其方法可以通过字符串（`Selector`）在运行时被动态调用。编译器无法静态地追踪所有可能的 `Selector` 调用。

3.  **XIB/Storyboard 中的引用**: 通过 Interface Builder 创建的 `IBOutlet` 和 `IBAction`，其连接是在运行时建立的，编译器同样无法静态地分析其引用关系。

4.  **反射和 KVC**: 通过反射或 Key-Value Coding 访问的属性，也无法被编译器静态地检测到。

5.  **跨模块和组件化**: 在组件化的项目中，一个模块中的 `public` 代码，可能被其他多个模块所依赖。要确定其是否“无用”，需要进行全局的、跨模块的依赖分析。

## 无用代码检测工具与方法

由于编译器的局限性，我们需要借助一些静态分析工具和代码审查方法，来辅助我们查找无用代码。

### 1. Periphery

Periphery 是目前社区中最流行、最强大的 Swift 无用代码静态分析工具。

*   **工作原理**: 它通过模拟 Xcode 的编译过程，并利用 SourceKit 来分析源码，构建一个全局的符号依赖图。它能够比编译器更深入地理解 Swift 的语法和动态特性。
*   **优点**:
    *   **高准确率**: 能够识别出因动态派发、协议等原因而导致编译器无法移除的无用代码。
    *   **跨模块分析**: 支持对整个 Xcode Workspace 进行分析，找出跨模块的无用 `public` 代码。
    *   **可配置性**: 提供了丰富的配置选项，可以忽略特定的警告、排除某些文件或目录。
*   **使用方法**:
    ```bash
    # 安装
    brew install peripheryapp/periphery/periphery

    # 在项目根目录下运行
    periphery scan --project YourProject.xcodeproj --targets YourTarget
    ```

### 2. SourceKit-LSP + 自定义脚本

对于有更高定制化需求的大型项目，可以利用苹果官方的 `SourceKit-LSP`，来构建自己的无用代码分析工具。

*   **SourceKit-LSP**: 是一个实现了语言服务器协议（Language Server Protocol）的服务。它可以提供关于 Swift 代码的丰富信息，如符号定义、引用、类型信息等。
*   **工作流程**:
    1.  使用 SourceKit-LSP 的 `index` 功能，为整个项目创建一个符号索引数据库。
    2.  编写脚本（如 Python, Swift），解析这个索引数据库。
    3.  从程序的入口点开始，构建一个完整的调用图（Call Graph）。
    4.  所有未出现在调用图中的符号，即为潜在的无用代码。

### 3. 代码审查与人工判断

工具只能作为辅助，最终的判断仍然需要开发者来进行。

*   **废弃警告 (`@available`)**: 当你决定废弃一个 API 时，不要立即删除它。应该先使用 `@available` 将其标记为废弃，并提供替代方案。这可以给其他开发者一个迁移的过渡期。

    ```swift
    @available(*, deprecated, message: "Use newShinyMethod() instead")
    func oldMethod() { ... }
    ```

*   **代码覆盖率**: 运行单元测试并开启代码覆盖率分析。覆盖率为 0% 的代码，虽然不一定是“无用”的（可能只是测试用例不全），但它们是很好的、需要被重点审查的候选对象。

## 总结

清理无用代码，是一项需要长期坚持的、系统性的优化工作。

1.  **相信编译器**: 首先，确保你的 Release 版本开启了编译优化（Dead Code Stripping），编译器会自动为你完成大部分基础的清理工作。

2.  **善用工具**: 使用 **Periphery** 等静态分析工具，来定期地、自动化地扫描项目，以发现编译器无法处理的、更深层次的无用代码。

3.  **结合人工审查**: 对于工具扫描出的结果，需要结合业务逻辑和代码上下文，进行人工的确认和判断，以避免误删。

4.  **养成良好习惯**: 在日常开发中，就有意识地保持代码的整洁。对于不再使用的代码，及时地进行标记或移除。

通过将自动化工具与良好的开发实践相结合，我们可以有效地控制代码库的“熵增”，减小包体积，降低维护成本，让我们的项目保持健康和活力。
