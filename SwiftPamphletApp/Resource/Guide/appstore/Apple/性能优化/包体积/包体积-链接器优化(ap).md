# 包体积优化：链接器优化

链接器（Linker, `ld`）是编译流程的最后一步，它负责将所有编译好的目标文件（`.o`）和库文件（`.a`, `.dylib`）“粘合”在一起，生成最终的可执行文件。通过向链接器传递特定的参数，我们可以引导它进行更深度的优化，从而有效地减小最终二进制文件的大小。

## 1. 链接时优化 (Link-Time Optimization, LTO)

LTO 是最重要、也是最有效的链接器优化手段。它允许链接器在链接阶段，对整个项目进行全局性的代码分析和优化。

*   **工作原理**: 编译器将源代码编译成一种中间表示（LLVM Bitcode），而不是直接生成机器码。在链接时，链接器可以一次性地分析所有模块的 Bitcode，从而能够进行跨文件的优化，例如：
    *   **更彻底的函数内联**: 将其他文件中的小函数，直接内联到调用处。
    *   **更精准的无用代码剥离**: 识别并移除那些在整个项目中，从未被调用过的 `public` 或 `internal` 函数。
*   **如何开启**: 在 `Build Settings -> Linking -> Link-Time Optimization` 中，为 Release 配置选择 `Incremental` (增量式) 或 `Monolithic` (整体式)。

（更多详情请参阅 `包体积-编译优化(ap).md`）

## 2. Order File (顺序文件)

Order File 是一种可以显著优化 App **启动速度**，并对**包体积**有一定正面影响的技术。

*   **工作原理**: 它是一个纯文本文件，其中包含了按特定顺序列出的函数符号。在链接时，我们可以将这个文件提供给链接器。链接器会按照这个文件中指定的顺序，来排列最终可执行文件中的函数代码的物理布局。

*   **对启动速度的影响**: 我们可以通过工具（如 AppOrderFiles），来记录 App 在启动阶段，实际调用的所有函数的顺序。然后，将这个顺序生成一个 Order File。这样，链接器就会将所有启动时需要用到的函数，都紧密地、连续地排列在可执行文件的最前面。当 App 启动时，操作系统就可以通过一次或几次连续的 I/O 操作，将所有必要的代码，一次性地从闪存加载到物理内存中，极大地减少了因“缺页中断”（Page Fault）而带来的随机 I/O 开销，从而加快启动速度。

*   **对包体积的影响**: 将功能相关的函数，在物理上排列在一起，可以提高代码的局部性（locality）。这使得 CPU 的指令缓存（i-cache）能够更有效地工作。同时，对于 ARM64 架构，连续的指令之间，可以使用更短的、相对寻址的跳转指令，而不是更长的绝对地址跳转指令，从而在微观上，节省了一部分代码体积。

*   **如何生成和使用**:
    1.  在 `Build Settings -> Linking -> Order File` 中，指定你的 `.order` 文件的路径。
    2.  在 `Build Settings -> Linking -> Write Link Map File` 中，开启 Link Map 的生成，以便后续分析。

## 3. 链接器脚本 (Linker Script)

对于有极高优化需求的、复杂的项目（例如，大型的组件化项目），可以通过自定义链接器脚本，来更精细地控制最终二进制文件的布局和内容。这是一种非常高级的、专家级的优化手段。

*   **功能**: 
    *   **段合并 (Segment Merging)**: 将多个功能类似的、但分散在不同库中的段（Segment），合并在一起。
    *   **符号排除**: 强制链接器在链接时，排除掉某些你确定不需要的符号。

## 4. 分析 Link Map 文件

Link Map 文件是链接器在生成可执行文件时，产生的一个详细的“地图”。它记录了最终二进制文件中，每一个符号（函数、变量）的地址、大小，以及它来自于哪个目标文件（`.o`）。

通过编写脚本来解析 Link Map 文件，我们可以：

*   **精确地分析包体积构成**: 统计出项目中每一个类、每一个第三方库，在最终的可执行文件中，所占用的具体大小。
*   **发现异常**: 快速地定位到那些异常增大的模块或函数，从而进行针对性的优化。

## 总结

链接器优化，是包体积治理中一个相对底层、但非常有效的环节。

1.  **开启 LTO**: 这是最简单、也最重要的链接器优化。在 Release 配置下，务必开启**增量式 LTO**。

2.  **使用 Order File**: 通过优化代码在二进制文件中的物理布局，来提升启动性能，并对包体积产生积极的附带效应。

3.  **分析 Link Map**: 将 Link Map 文件的分析，作为包体积监控的常规手段，可以让我们对二进制文件的构成，有更清晰、更量化的认识。

通过这些链接器层面的优化，我们可以让构建系统，在“最后一公里”，为我们的 App 包体积，进行一次彻底的“压缩”和“整理”。
