# OC 项目启动时间分析

对于以 Objective-C 为主要开发语言的成熟项目，其启动时间的构成和优化重点，与纯 Swift 项目既有共通之处，也有其独特的挑战。这主要源于 Objective-C 语言的动态特性和其运行时的实现机制。

## 启动时间的两个阶段

与所有 iOS App 一样，OC 项目的启动时间，也可以分为两大阶段：

1.  **pre-main 阶段**: 从用户点击 App 图标，到 `main` 函数执行第一行代码之间的阶段。这个阶段完全由操作系统和动态链接器（`dyld`）主导。

2.  **main 阶段**: 从 `main` 函数开始，到第一个界面的 `viewDidAppear` 执行完成的阶段。这个阶段主要由我们自己的代码所控制。

## pre-main 阶段的耗时分析

在 OC 项目中，pre-main 阶段的耗时，主要集中在以下几个方面。我们可以通过在 Xcode 中设置环境变量 `DYLD_PRINT_STATISTICS` 为 `1` 来精确地测量它们。

### 1. dylib loading (动态库加载)

*   **原因**: `dyld` 需要找到、验证并加载 App 所依赖的所有动态库（`.dylib` 或 `.framework`）。
*   **OC 项目的特点**: 大型 OC 项目，特别是采用组件化架构的，通常会依赖大量的自定义动态库。**动态库的数量，是影响这一阶段耗时的最主要因素。**
*   **优化**: 
    *   **减少动态库数量**: 将非必要的动态库，改为静态链接。
    *   **使用“可合并库”**: 对于 Xcode 15+，开启“Mergeable Libraries”功能，将多个动态库，在链接时自动合并成一个。

### 2. rebase/binding (重定位/绑定)

*   **原因**: 由于 ASLR（地址空间布局随机化）的存在，动态库在加载到内存时，其地址是随机的。`dyld` 需要修正代码中所有指向这些动态库内部的指针和符号的地址（Rebasing），并将你的代码与这些外部符号进行绑定（Binding）。
*   **OC 项目的特点**: OC 的动态性（如 `selector` 的实现），依赖于大量的符号绑定。动态库越多，需要绑定的符号也越多。
*   **优化**: 核心仍然是**减少动态库的数量**。

### 3. ObjC setup (Objective-C 运行时设置)

*   **原因**: 这是 OC 项目特有的一个耗时阶段。`dyld` 在加载完所有代码后，需要通知 Objective-C 的运行时，来进行一系列的初始化工作。
*   **主要工作**:
    *   **注册所有 OC 类**: 运行时需要读取所有编译进来的类的信息，并将其注册到一个全局的类表中。
    *   **Category 的附加**: 将所有 Category 中定义的方法和属性，附加到其主类上。
    *   **保证 `selector` 的唯一性**: 运行时需要确保每一个 `selector` 的名称，在全局是唯一的。
*   **优化**: 
    *   **减少类的数量**: 清理项目中无用的 OC 类。
    *   **减少 Category 的数量**: 特别是对于大型的基础类（如 `NSObject`, `UIView`）的 Category，应该谨慎使用。
    *   **减少 `selector` 的数量**: 清理无用的方法。

### 4. initializers (初始化器)

*   **原因**: `dyld` 在这个阶段，会执行所有 OC 的 `+load` 方法，以及 C/C++ 的构造函数（`__attribute__((constructor))`）。
*   **`+load` 方法的危害**: `+load` 方法是在类被加载到内存时，就**立即、同步地**执行的。如果大量的类都实现了 `+load` 方法，并且在其中进行了耗时操作，会严重地拖慢启动速度。
*   **优化**: 
    *   **彻底消灭 `+load` 方法**: 这是启动优化的一个重要原则。应该将 `+load` 中的所有代码，都转移到 `+initialize` 方法中。
    *   **`+initialize` 的优势**: `+initialize` 方法，是在一个类**第一次收到消息**时，才会被“懒加载”式地调用的。这使得我们可以将初始化操作，分散到 App 的整个运行生命周期中，而不是全部堆积在启动阶段。

## main 阶段的耗时分析

`main` 阶段的优化，与 Swift 项目类似，核心是**延迟和异步**。

*   **`application(_:didFinishLaunchingWithOptions:)` 的瘦身**: 
    *   只保留与首屏渲染直接相关的、必须同步执行的代码。
    *   将所有第三方 SDK 的初始化、数据预加载、日志系统配置等，全部异步地派发到后台线程。
    *   对于需要初始化的单例，全部使用 `dispatch_once` 或其他懒加载方式，来确保它们只在第一次被使用时，才进行初始化。

## 总结

对于 OC 项目的启动优化，其核心思路与 Swift 项目是一致的，但由于其语言特性，侧重点有所不同。

*   **pre-main 阶段是重灾区**: 由于 OC 的动态性和历史原因，大型 OC 项目通常存在大量的动态库、Category 和 `+load` 方法。因此，`pre-main` 阶段的优化，往往是 OC 项目启动优化的重中之重。

*   **优化清单**:
    1.  **合并动态库**: 减少动态库的数量，是优化 `dylib loading` 和 `rebase/binding` 耗时的最有效手段。
    2.  **消灭 `+load`**: 将所有 `+load` 方法，都改造为 `+initialize`，是优化 `ObjC setup` 和 `initializer` 耗时的关键。
    3.  **精简类和 Category**: 减少无用的 OC 类和 Category，可以直接地降低 `ObjC setup` 的工作量。
    4.  **异步化 `didFinishLaunching`**: 将所有非首屏必须的任务，都从 `didFinishLaunching` 中移出，异步地在后台执行。
