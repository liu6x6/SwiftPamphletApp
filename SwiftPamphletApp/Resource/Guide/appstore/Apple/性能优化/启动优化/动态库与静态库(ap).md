# 动态库与静态库

在 iOS/macOS 开发中，库（Library）是预先编译好的、可被多个项目复用的代码和资源的集合。理解不同类型的库及其链接方式，对于我们进行 App 架构设计、包体积优化和启动性能优化，至关重要。

库主要分为两种类型：**静态库（Static Libraries）**和**动态库（Dynamic Libraries）**。

## 1. 静态库 (Static Libraries)

*   **文件格式**: `.a` (Archive) 或 `.xcframework` (包含 `.a` 文件)。
*   **链接方式**: **静态链接 (Static Linking)**。
*   **工作原理**: 在应用的**编译链接**阶段，静态库的代码和数据，会被**完整地、直接地拷贝**到你的 App 的最终可执行文件中。链接器会将你的代码和静态库的代码，合并成一个单一的、庞大的二进制文件。

### 优点

1.  **启动速度快**: 由于所有代码都在一个可执行文件中，App 启动时，无需再去加载和链接外部的库文件，启动过程更简单、更快速。
2.  **包体积优化**: 链接器在进行静态链接时，可以进行更彻底的“死代码剥离”（Dead Code Stripping）。这意味着，如果一个静态库中，有你从未使用过的代码，那部分代码将**不会**被包含在最终的可执行文件中，从而减小了包体积。
3.  **无兼容性问题**: 因为库的代码已经成为了你 App 的一部分，所以不存在因操作系统升级、导致外部动态库版本不兼容的问题。

### 缺点

1.  **包体积冗余**: 如果多个 App 或 App Extension 都使用了同一个静态库，那么这个库的代码，会在每一个可执行文件中，都存在一份拷贝，造成了存储空间的浪费。
2.  **编译时间长**: 每次编译，都需要重新链接所有的静态库代码。
3.  **更新不便**: 如果静态库本身有更新，所有依赖它的 App，都必须重新编译和发布。

## 2. 动态库 (Dynamic Libraries)

*   **文件格式**: `.dylib` 或 `.framework` (包含 `.dylib` 文件)。
*   **链接方式**: **动态链接 (Dynamic Linking)**。
*   **工作原理**: 在编译时，链接器并不会将动态库的代码拷贝到你的可执行文件中。它只是记录下了一个“符号存根”（stub），表明“我将来需要用到这个库里的这个函数”。
    在 App **启动或运行时**，动态链接器（`dyld`）会根据这些记录，去加载实际的动态库文件到内存中，然后再将你的代码与库中的代码，进行“绑定”（binding）。

### 优点

1.  **代码共享，节省内存**: 多个进程可以共享内存中同一份动态库的副本。例如，所有的 iOS App，都共享操作系统中的 `UIKit.framework` 和 `Foundation.framework`。这极大地节省了物理内存。
2.  **易于更新**: 动态库可以独立于主应用进行更新。例如，操作系统可以通过一次系统更新，来修复所有 App 都在使用的某个系统框架的 Bug。
3.  **模块化**: 有利于代码的模块化和解耦。

### 缺点

1.  **启动性能开销**: App 启动时，`dyld` 需要花费额外的时间，去加载、重定位（Rebase）和绑定（Bind）所有依赖的动态库。如果 App 依赖的自定义动态库过多，会显著地拖慢 App 的启动速度（特别是 pre-main 阶段）。
2.  **包体积较大**: 整个动态库文件，无论其内部的代码是否被全部使用，都会被完整地拷贝到你的 App Bundle 中。链接器无法对其进行跨库的死代码剥离。

## 静态库 vs. 动态库：如何选择？

| 特性 | 静态库 | 动态库 |
| :--- | :--- | :--- |
| **链接时间** | 编译时 | 启动/运行时 |
| **代码拷贝** | 拷贝到可执行文件 | 独立文件，不拷贝 |
| **启动性能** | **快** | **慢** (有加载和绑定开销) |
| **包体积** | **可能更小** (得益于死代码剥离) | **可能更大** (整个库被拷贝) |
| **代码共享** | 不支持 | 支持 (系统库) |
| **更新** | 需重新编译主 App | 可独立更新 |

### 优化建议

*   **第三方库**: 对于你项目中的第三方依赖（如通过 CocoaPods, Carthage, SPM 管理的库），如果它们不是被多个 Target（如主 App 和多个 App Extension）所共享，**强烈建议使用静态链接的方式**来集成它们。这可以显著地减少动态库的数量，加快启动速度，并减小包体积。
    *   在 CocoaPods 中，可以通过 `use_frameworks!(linkage: :static)` 来实现。

*   **业务模块**: 对于你自己的业务模块，需要进行权衡。
    *   如果一个模块，被主 App 和多个 App Extension 所共享，将其做成**动态库**，可以避免代码的重复拷贝。
    *   如果一个模块，只被主 App 所使用，将其做成**静态库**，通常是更好的选择。

## 总结

静态库和动态库，是两种不同的代码复用和分发方式，它们各有优劣。

*   **静态库**以“空间换时间”，通过在编译时将代码合并，来换取更快的启动速度和更优化的代码体积。
*   **动态库**以“时间换空间”，通过在运行时加载和共享代码，来节省内存和磁盘空间，但会带来启动时的性能开销。

在进行 App 架构设计和性能优化时，理解并合理地选择库的链接方式，是一项至关重要的工作。总的原则是：**在不牺牲必要的模块化和代码共享的前提下，尽可能地减少自定义动态库的数量，优先使用静态链接。**
