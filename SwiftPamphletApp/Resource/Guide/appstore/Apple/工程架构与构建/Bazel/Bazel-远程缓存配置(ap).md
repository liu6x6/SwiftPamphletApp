# Bazel 远程缓存配置 (Remote Caching)

对于超大型的 iOS 团队而言，将项目迁移到 Bazel 的最大动力之一，就是它那近乎魔法般的**远程缓存 (Remote Caching)** 能力。这也是解决构建速度瓶颈的“终极杀器”。

## 1. 什么是远程缓存？

在没有远程缓存时，如果你在一个拥有几千个模块的工程里做全量编译（Clean Build），你的电脑需要从头到尾编译这几千个模块。

开启了远程缓存后：
1. **开发者 A** (或者 CI 服务器) 在半小时前刚好编译过 `NetworkModule` (版本号的 Hash 没变)。
2. 编译产生的 `.o` (目标文件) 或 `.a` (静态库) 产物会被上传到一个公司内网的**远端缓存服务器**上。
3. 当**开发者 B** 此时拉取最新代码并执行全量编译时，Bazel 的引擎在编译 `NetworkModule` 之前，会计算该模块的输入（源码文件、依赖树、编译器参数）生成的 Hash Key。
4. Bazel 向缓存服务器发起询问："你那里有没有这个 Hash 的产物？"。
5. 服务器回答："有！"。Bazel 就会**直接下载这个二进制文件**，跳过编译这个模块的耗时。

结果就是：原本需要 40 分钟的全量编译，可能只需要 3 分钟的下载时间。

## 2. 远程缓存的底层原理与挑战：Hermeticity (密封性)

要让缓存能够被完美复用，构建环境必须具备 **Hermeticity (密封性 / 确定性)**。
这意味着，给定相同的输入，输出必须是**绝对一致且可复现**的。

如果构建系统读了当前的时间戳写进代码，或者用到了绝对路径，或者依赖了不同开发者电脑上版本不一致的 Xcode，那么它们算出来的 Hash 就不一样，缓存就会命中失败 (Cache Miss)。

为此，Bazel 做了非常严格的沙盒隔离（Sandbox），强制你把所有编译器工具链（包括特定版本的 Swift 编译器）都作为依赖声明出来，确保张三和李四在不同电脑上构建的行为是完全确定的。

## 3. 如何配置远端缓存

远程缓存后端可以使用很多支持 gRPC 或 HTTP(S) 协议的服务器，例如：
*   **bazel-remote** (开源的高性能缓存服务器)
*   Nginx (配置 WebDAV 模块作为 HTTP 缓存)
*   Google Cloud Storage / Amazon S3
*   Buildbarn

### HTTP 缓存配置示例
在你的工程根目录下的 `.bazelrc` 文件中，加入以下配置：

```bash
# 启用远端 HTTP 缓存，指向公司的缓存服务器
build --remote_cache=http://bazel-cache.mycompany.com:8080

# (可选) 允许向服务器上传你编译好的缓存。
# 通常只允许 CI 服务器上传，普通开发者的机器只下载不上传，以免污染缓存。
# build --remote_upload_local_results=true 
```

## 4. 远程执行 (Remote Execution)

除了远程缓存，Bazel 更高阶的玩法是**远程执行 (Remote Execution, RE)**。
*   **远程缓存**：你自己电脑负责“执行编译和判断”，只是能直接下载别人做好的结果。如果遇到没有缓存的模块，还是得燃烧你自己的 CPU。
*   **远程执行**：你的电脑把“源码和指令”发送给云端的**编译集群**（比如一个有几百个核心的构建农场）。云端几百台机器并行帮你编译，然后把最终打包好的 App 传回给你。

Apple 生态做远程执行的难点在于：iOS 代码必须在 macOS 环境下编译（虽然现在 Swift 可以跨平台，但链接 UIKit 和签名依然需要 Mac）。搭建和维护一个庞大的 Mac 集群（如 Mac Mac Studio 阵列）成本是极其高昂的。因此大多数大厂在 iOS 上通常只做 Remote Caching，而非 Remote Execution。
