# 移动端开发中的设计模式

设计模式（Design Patterns）是在软件设计中，针对特定问题的一套经过验证的、可复用的解决方案。它们不是具体的代码，而是一种解决问题的思想和模式。在移动应用开发中，合理地运用设计模式，可以极大地提高代码的可读性、可维护性、可扩展性和可测试性。

## 核心思想：解耦与复用

几乎所有设计模式的最终目的都是为了**解耦（Decoupling）**——即降低不同代码模块之间的依赖关系。一个低耦合的系统更容易被修改、扩展和测试。

## 常见的设计模式分类

设计模式通常被分为三大类：创建型、结构型和行为型。

### 1. 创建型模式 (Creational Patterns)

这类模式关注于**对象的创建过程**，旨在将对象的创建与使用分离开来，使得系统在创建对象时具有更大的灵活性。

*   **单例模式 (Singleton)**
    *   **作用**: 确保一个类只有一个实例，并提供一个全局访问点。
    *   **iOS 中的例子**: `UserDefaults.standard`, `FileManager.default`, `URLSession.shared`。
    *   **优点**: 简单，保证唯一实例。
    *   **缺点**: 引入全局状态，难以测试，隐藏依赖。
    *   **现代实践**: 谨慎使用。对于非全局性的服务，优先考虑**依赖注入**。

*   **工厂模式 (Factory)**
    *   **作用**: 定义一个用于创建对象的接口，但让子类决定实例化哪一个类。工厂方法使一个类的实例化延迟到其子类。
    *   **例子**: 一个 `ViewFactory`，根据传入的 `ViewModel` 类型，创建并返回不同的 `View`。
    *   **优点**: 将对象的创建和使用分离，客户端代码无需关心具体的类名。

*   **建造者模式 (Builder)**
    *   **作用**: 将一个复杂对象的构建与其表示分离，使得同样的构建过程可以创建不同的表示。
    *   **例子**: `URLComponents` 就是一个建造者模式的例子，你可以通过设置它的 `scheme`, `host`, `path`, `queryItems` 等属性，来逐步构建一个复杂的 `URL`。
    *   **优点**: 可以分步构建复杂对象，代码可读性好。

### 2. 结构型模式 (Structural Patterns)

这类模式关注于**如何组合类和对象**，以形成更大的、更灵活的结构。

*   **适配器模式 (Adapter)**
    *   **作用**: 将一个类的接口转换成客户端所期望的另一个接口。使得原本由于接口不兼容而不能一起工作的那些类可以一起工作。
    *   **iOS 中的例子**: 在 SwiftUI 中使用 `UIViewRepresentable` 或 `UIViewControllerRepresentable` 来封装一个 UIKit 组件，就是典型的适配器模式。它将 `UIView` 的接口“适配”成了 SwiftUI 的 `View` 接口。

*   **外观模式 (Facade)**
    *   **作用**: 为一个复杂的子系统提供一个简化的、统一的接口。客户端只需要与这个外观接口交互，而无需关心子系统内部的复杂实现。
    *   **例子**: 创建一个 `NetworkManager` 类，它内部封装了 `URLSession`、请求构建、JSON 解析、错误处理等一系列复杂操作，但只向外暴露一个简单的 `fetchData(from:completion:)` 方法。

*   **装饰器模式 (Decorator)**
    *   **作用**: 动态地给一个对象添加一些额外的职责。就增加功能来说，装饰器模式相比生成子类更为灵活。
    *   **SwiftUI 中的例子**: SwiftUI 的**修饰符 (Modifier)** 体系就是装饰器模式的完美体现。每个修饰符（如 `.padding()`, `.background()`, `.shadow()`）都像一个装饰器，它接收一个 `View`，然后返回一个被“装饰”过的、具有新外观或行为的新 `View`。

### 3. 行为型模式 (Behavioral Patterns)

这类模式关注于**对象之间的通信和职责分配**。

*   **观察者模式 (Observer)**
    *   **作用**: 定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都将得到通知并自动更新。
    *   **iOS 中的例子**: 这是响应式编程的核心。
        *   `NotificationCenter`: 经典的观察者模式实现。
        *   **Combine 框架 / RxSwift**: 提供了 `Publisher` (被观察者) 和 `Subscriber` (观察者) 的完整实现。
        *   **SwiftUI 的数据流**: `@State`, `@Published`, `@ObservedObject` 等属性包装器，其底层就是观察者模式。当 `@Published` 属性变化时，所有观察该对象的视图都会收到通知并刷新。

*   **策略模式 (Strategy)**
    *   **作用**: 定义一系列的算法，把它们一个个封装起来，并且使它们可以相互替换。此模式让算法的变化独立于使用算法的客户。
    *   **例子**: 一个图片加载器，可以根据网络状况或用户设置，在“高质量加载策略”、“低质量加载策略”和“仅 Wi-Fi 加载策略”之间进行切换。

*   **命令模式 (Command)**
    *   **作用**: 将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化；对请求排队或记录请求日志，以及支持可撤销的操作。
    *   **iOS 中的例子**: `UndoManager` 就是命令模式的经典应用。每个可撤销的操作（如文本输入、删除）都被封装成一个命令对象，`UndoManager` 负责维护这些命令的栈，以实现撤销和重做。

*   **代理模式 (Delegate)**
    *   **作用**: 一个对象（委托人）将它需要处理的某些任务，委托给另一个对象（代理人）来完成。委托人只定义一个协议（`protocol`），其中包含了它希望代理人实现的方法。
    *   **iOS 中的例子**: 这是 `UIKit` 中最最常见的设计模式。`UITableViewDelegate`, `UITextFieldDelegate` 等都是典型的例子。`UITableView` 不关心如何响应用户的点击，它只在被点击时调用其 `delegate` 的 `tableView(_:didSelectRowAt:)` 方法，将具体的行为“委托”出去。

## SwiftUI 与设计模式

SwiftUI 的出现，使得某些传统设计模式的重要性发生了变化：

*   **MVVM 成为主流**: SwiftUI 的数据绑定特性与 MVVM 模式天然契合。
*   **装饰器模式无处不在**: 修饰符系统是装饰器模式的最佳实践。
*   **观察者模式是核心**: 整个 SwiftUI 的状态驱动更新机制都建立在观察者模式之上。
*   **代理模式被淡化**: 在纯 SwiftUI 中，我们更多地使用闭包回调（如 `Button` 的 `action`）和数据绑定（`@Binding`）来替代代理模式，以实现父子视图间的通信。

## 总结

设计模式是前人智慧的结晶，是软件工程的最佳实践。学习和理解设计模式，不是为了生搬硬套，而是为了：

*   **拥有更丰富的“词汇量”**: 能够用标准的、通用的语言来讨论和设计复杂的系统。
*   **获得更优的“工具箱”**: 在面对具体问题时，能够快速地从工具箱中找到经过验证的、优雅的解决方案。
*   **写出更健壮的代码**: 构建出低耦合、高内聚、易于测试和维护的应用程序。

对于移动开发者来说，深入理解 MVVM、观察者、适配器、外观、单例（及其替代方案）等核心模式，是从“能写代码”到“会写好代码”的必经之路。
