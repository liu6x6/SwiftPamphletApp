# 跨平台方案中的布局与渲染机制

当我们在讨论各种跨平台框架（如 React Native, Flutter, Weex 等）时，决定其性能上限和跨端一致性的核心技术环节，在于它们的**布局（Layout）**和**渲染（Rendering）**机制。

## 1. 布局 (Layout) 引擎

布局系统负责计算界面上每个元素（如按钮、图片、文字）的坐标（X, Y）和大小（Width, Height）。

由于不同平台的原生布局系统差异巨大（iOS 的 Auto Layout vs Android 的 LinearLayout/ConstraintLayout），为了实现跨平台，必须有一个**统一的布局计算引擎**。

### Flexbox 与 Yoga / Yoga 引擎
目前跨平台领域事实上的工业标准是 **Flexbox**。
*   **Yoga (由 Meta/Facebook 开源)**：这是一个用 C++ 编写的、极速的跨平台 Flexbox 布局引擎。React Native、Weex 以及众多大厂自研框架（如字节 Lynx 早期版本）底层全部使用了 Yoga。
*   **工作流**：开发者在 JS 层用类似 CSS 的 Flex 语法描述布局树 -> 数据传递给底层的 C++ Yoga 引擎 -> Yoga 飞速计算出所有节点的绝对坐标的 CGRect -> 传递回原生系统进行摆放。

## 2. 渲染 (Rendering) 架构演进

计算好位置后，如何把它们“画”到屏幕上？这分为两大技术流派：**原生渲染** 和 **自绘渲染**。

### 流派 A：原生映射渲染 (Native UI Rendering)
代表：React Native, Weex
1.  **架构**：在 JavaScript 环境中维护一棵虚拟 DOM 树。当数据变化时，JS 层计算出 DOM 树的差异（Diff）。
2.  **桥接 (Bridge)**：将这些差异指令通过 JSBridge 序列化发送给原生（iOS/Android）层。
3.  **实例化**：原生层接收到指令后，实例化真实的 `UILabel`、`UIImageView`（iOS）或 `TextView`、`ImageView`（Android）。
4.  **优点**：组件拥有绝对原生的手感，可以直接利用系统提供的无障碍（Accessibility）功能和输入法。
5.  **缺点**：
    *   **JSBridge 瓶颈**：当页面极其复杂、动画高频触发时，JS 线程和原生主线程之间的序列化/反序列化通信会导致严重的掉帧卡顿。
    *   **表现不一致**：原生组件在两端的实现细节不同，经常导致一个圆角或阴影在 iOS 上正常，在 Android 上就被裁剪。

### 流派 B：自绘渲染引擎 (Custom Rendering Engine)
代表：Flutter
1.  **架构**：完全抛弃系统的原生 UI 组件体系（不要 `UIView`，也不要 `TextView`）。框架只向操作系统要一块画布（Canvas）和监听屏幕触摸事件的权限。
2.  **引擎管线**：使用 C/C++ 编写的底层图形引擎（如 Google 的 Skia 或 Impeller）。框架自己实现了一套极其庞大的 UI 组件库（从绘制圆角、渲染文本字形、到实现滚动惯性物理模型）。
3.  **优点**：
    *   **极高的性能**：跳过了昂贵的通信桥梁，直接将渲染指令发送给 GPU。
    *   **像素级的一致性**：无论在 iOS 还是 Android 上运行，只要用的是同一个引擎，画出来的每一根像素线都是绝对一样的。
    *   **高帧率动画**：轻松跑满 60fps 甚至 120fps。
4.  **缺点**：
    *   引擎体积庞大，增加包体积。
    *   难以与现有项目里的老旧原生界面（比如一个复杂的地图组件）完美嵌套融合。
    *   当苹果或谷歌发布了新的系统 UI 风格（比如 iOS 15 的新毛玻璃效果），自绘引擎必须等社区手动用代码“模仿”实现一遍，永远慢半拍。

## 3. 架构的融合趋势

为了解决 JSBridge 的瓶颈，**React Native 的新架构 (Fabric)** 引入了 JSI（直接进行 C++ 到 JS 引擎的同步调用，抛弃异步的 JSON 序列化通信），极大地拉近了与 Flutter 的性能差距。跨平台技术正朝着“融合底层 C++ 能力”的方向殊途同归。
