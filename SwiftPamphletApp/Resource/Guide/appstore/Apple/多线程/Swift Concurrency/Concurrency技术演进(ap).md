# Swift 并发技术的历史演进

要深刻理解 Swift Concurrency (`async/await`) 到底牛在哪里，我们就必须回顾 Apple 平台历史上极其坎坷的“多线程防卡死”斗争史。

## 第一纪元：NSThread 与 Pthreads (远古时代)

在 iPhone 诞生的初期（甚至更早的 Mac OS X 时代），如果你不想让极其耗时的图片下载卡死主界面，你必须手动创建一个 `Thread` (线程)。

*   **痛苦之处**：你必须自己负责线程的启动、挂起、睡眠和销毁。你还要小心翼翼地使用 `NSLock` 或 `Mutex` (互斥锁) 来保护共享变量。由于创建一个线程消耗的系统内存巨大，如果程序员水平不高，随手 `new Thread` 几十个，App 瞬间就会崩溃。

## 第二纪元：GCD (Grand Central Dispatch) / NSOperationQueue (革命性的进步)

为了不让程序员接触到底层的吃人线程，Apple 在 2009 年推出了轰动业界的 **GCD (C语言接口)** 和基于它封装的 **NSOperation (面向对象接口)**。

*   **核心思想：线程池 (Thread Pool) 与 队列 (Queue)**。
    程序员不再自己创建线程了！你只需要把“要干的活（闭包 Blocks）”打包，扔进一个名叫 `DispatchQueue` 的管子里。系统在底层自动养着一池子线程，系统看哪个线程闲着，就让他从管子里把活拿出来干。
*   **带来的灾难：回调地狱 (Callback Hell)**。
    活干完了，为了把结果送回主线程，你必须在闭包的深处再嵌套一个闭包：
    ```swift
    DispatchQueue.global().async {
        let result = doHeavyWork() // 后台干活
        DispatchQueue.main.async { 
            self.label.text = result // 切回前台刷新
        }
    }
    ```
    嵌套三四层后，代码缩进极其恐怖，且错误（Error）极难向外传递。

## 第三纪元：FRP / RxSwift 与 Combine (声明式数据流)

为了解决 GCD 的闭包嵌套之痛，社区先是发扬光大了 **RxSwift**，随后苹果官方下场推出了 **Combine**。

*   **核心思想**：把异步操作抽象成“可以被订阅的、源源不断流水的水管”。利用极其丰富的操作符（`map`, `flatMap`, `zip`）在水管中间对数据进行变换。
*   **局限性**：学习曲线极高（需要理解弹珠图、背压等复杂概念）。而且对于绝大多数“只是想简单发个请求然后拿个结果”的单次任务来说，架设这么一套庞大的水管系统显然是杀鸡用牛刀。

## 第四纪元：Swift Concurrency (语言级别的降维打击)

在吸收了 C#、Kotlin 和 Rust 等现代语言的优秀经验后，Swift 5.5 终于迎来了终极的并发模型：**`async` / `await` 与 `Actors`**。

*   **真正的协程 (Coroutines) 与延续 (Continuations)**。
    当代码执行到 `await` 时，当前的函数会被**挂起 (Suspended)**，但它所占用的底层系统线程**绝对没有被阻塞**！这个宝贵的线程会立刻被系统抽调去执行其他人的任务。等网络请求几秒钟后真正回来了，系统会把刚才挂起的函数恢复（Resume），找个有空的线程接着往下跑。
*   **结构化**：用 `TaskGroup` 让并发任务的生老病死有迹可循。
*   **绝对安全**：用 `actor` 和 `Sendable` 检查，让编译器在编译打包前，就把你可能因为多线程抢夺同一块内存而导致的 Crash 提前掐死在摇篮里。

**总结**：Swift 的并发演进，是一条**从“程序员管理物理线程”，走向“框架管理队列”，再进化到“编译器利用协程管理语法级生命周期”**的绝对现代化之路。
